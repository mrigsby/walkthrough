Check the app for accessibility problems, and write the accessibility report. Use the walkthrough skill, and follow `references/a11y-report.md` to write the text.

What to check: $ARGUMENTS

1. Find out what to check:
   - An argument that starts with `/` or `http` is a page.
   - An argument that ends in `.txt` is a file in the project with one page on each line. Read it. Skip empty lines and lines that start with `#`.
   - Any other argument is a plan name.
   - With no arguments, ask the developer which pages to check.
2. Check the pages:
   - For pages, call `a11y_scan` with `urls`. If the reply says to call it again with `runId`, do that until it has checked all pages.
   - For a plan, run it like `/walkthrough:run` does. Call `a11y_audit` for each "accessibility check" step. If the plan has no such steps, tell the developer and offer to scan its pages with `a11y_scan` instead.
3. Call `a11y_report` with the `runId`, and no items. Keep the `digest`.
4. If the app's source code is in this project, find where to fix each issue. Search the source for the markup in the findings, such as ids, class names, and visible text. Use `Grep` and `Read`. Add up to 3 places to `where` for each issue. If you cannot find an issue in the source, leave `where` out. Never guess a file.
5. Write `explain` and `fix` for every issue, and `code` when an example helps. Write a `summary` of 2 to 4 sentences. Follow `references/a11y-report.md`.
6. Call `a11y_report` again with `runId`, `digest`, `summary`, and `items`.
7. Tell the developer:
   - the score, and the three most serious issues
   - what is new, still there, or fixed, if the report compares with an earlier one
   - the path to `accessibility.html`
8. Show the suggested prompt from the reply in a code block. Tell the developer to paste it into a new session to plan the fixes.
